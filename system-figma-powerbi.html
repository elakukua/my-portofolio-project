Agree the dashboard on paper, before writing a single measure.

Building a dashboard is expensive to change and cheap to draw. Most rework in BI projects comes from discovering the design during the build, in front of stakeholders who are seeing it for the first time.

StackFigma · Power BI
RunsBefore every dashboard build
InvolvesProgramme, technical specialists, management
SavesRework cycles
STEP 01
↓
Establish the questions first

A dashboard is a set of answers. Drawing it starts with agreeing the questions and who is asking them.

What is needed
  • The decisions this dashboard is meant to support, stated as questions someone actually asks
  • The audience for each view — field team, management, donor — since they need different depth
  • The indicators available, and honesty about which questions the data cannot yet answer
Output
  • A short question list that becomes the specification for the layout
STEP 02
↓
Frame the layout in Figma

Wireframes at real proportions, so the conversation is about hierarchy and not about colour.

Process
  • Page structure first: how many views, what each one is for, how a user moves between them
  • Visual hierarchy: what must be readable in five seconds, what is available on inspection
  • Chart type chosen deliberately per question rather than by habit
  • Filter and slicer placement decided before the build, since retro-fitting these is disruptive
  • Brand-consistent colour, type and spacing applied as tokens rather than per-object choices
Output
  • A reviewable concept that looks like the finished product but costs a fraction to change
STEP 03
↓
Review before building

The review that would otherwise happen after two weeks of Power BI work happens here instead.

Process
  • Walk stakeholders through the frames as if using the dashboard, question by question
  • Capture change requests against the frames, where they cost minutes
  • Confirm which measures are needed — the frame list becomes the measure list
  • Sign off the concept explicitly, so the build has an agreed target
Why this step is the point
  • Stakeholders review a picture far more willingly than a working file they are afraid to break
  • Disagreements about what matters surface before any modelling work depends on the answer
STEP 04
Build to the frame

With the design settled, the Power BI work is modelling and measures rather than design decisions made under time pressure.

Process
  • Data model and measure library built against the agreed question list
  • Layout reproduced from the frames, including spacing and hierarchy
  • Design tokens carried across so the dashboard matches organisational brand standards
  • The frames retained as documentation of what was agreed and why
Result
  • Fewer build-and-revise cycles, and a dashboard whose layout has a stated rationale
What this changes in practice
  • Design decisions stop being made at 11pm. They are made in a review, deliberately, by the people who will use the result.
  • The measure list is derived, not guessed. Each measure exists because a frame needs it.
  • Brand consistency is built in. Tokens are set once in the concept rather than approximated per visual.
