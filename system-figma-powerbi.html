Design the dashboard as a prototype, then build to it.

A dashboard is expensive to change and cheap to draw. Framing the UI/UX in Figma first means the Power BI build starts from an agreed reference instead of discovering the design while building it.

Design-to-build flow — each stage is a reference for the next

01

Questions

  • The decisions the dashboard must support, written as questions someone actually asks
  • Audience per view: field team, management, donor — each needs different depth
  • Honest note on which questions the data cannot yet answer
02

Wireframe

  • Page structure: how many views, what each is for, how a user moves between them
  • Visual hierarchy: what must read in five seconds
  • Chart type chosen per question rather than by habit
03

UI frame

  • Layout at real proportions with spacing, type scale and colour tokens applied
  • Brand standards set once as tokens, not per object
  • Filter and slicer placement decided here — retro-fitting these is disruptive
04

Prototype

  • Frames linked so reviewers can click through as if using the dashboard
  • Interaction states shown: filtered, empty, drill-down
  • Costs minutes to change what would take a day in Power BI
05

Review

  • Walk stakeholders through the prototype question by question
  • Change requests captured against frames, where they are cheap
  • The frame list becomes the measure list
  • Concept signed off, so the build has an agreed target
06

Build in Power BI

  • Data model and measures built against the agreed question list
  • Layout reproduced from the frames, including spacing and hierarchy
  • Frames retained as documentation of what was agreed and why
