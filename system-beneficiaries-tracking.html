Google Forms → BigQuery → Looker Studio

Beneficiary tracking that is current, not compiled.

Most beneficiary tracking tables are a compilation exercise: someone collects workbooks, merges them, and the number is already out of date by the time it is read. This replaces that cycle with a pipeline.

STEP 01
↓
Define the record before the form

The unit of the table is one beneficiary interaction. Everything else follows from defining that precisely.

What is needed
  • An agreed definition of who counts as a beneficiary for each project type — direct, indirect, participant, reached
  • The disaggregation the logframe and donor both require: sex, age band, disability, location
  • A unique identifier convention that works across projects without exposing personal data
  • Consent wording and a data protection position agreed before any collection
Why it matters
  • Double counting almost always originates here, not in the pipeline — the same person recorded twice under two project labels
  • If the identifier is designed after collection begins, deduplication becomes guesswork
STEP 02
↓
Build the intake form

A Google Form as the single entry point, with validation doing as much of the quality work as possible at the moment of entry.

Process
  • Field-level validation: required fields, response ranges, controlled dropdowns instead of free text
  • Conditional logic so enumerators only see questions relevant to the project and beneficiary type
  • Location captured from a fixed list rather than typed, so it joins cleanly downstream
  • One form, many projects — a project field routes the record rather than each project maintaining its own form
Output
  • A single intake instrument that produces structurally identical records regardless of who fills it
STEP 03
↓
Land the data in BigQuery

Responses flow into a warehouse table rather than living in a spreadsheet that someone eventually copies.

Process
  • Raw responses land untouched in a staging table — the original is never overwritten
  • A transformation step handles typing, date parsing, category harmonisation and identifier construction
  • Deduplication logic runs against the identifier, flagging rather than silently deleting suspected duplicates
  • A clean table is the only object the dashboard reads from
Why a warehouse and not a sheet
  • Spreadsheets degrade as they grow: formulas break, rows get sorted, versions multiply
  • The staging-then-clean pattern means a bad transformation can be re-run without losing the source data
STEP 04
Publish to Looker Studio

The dashboard reads the clean table directly, so what a manager sees is what the pipeline produced — no intermediate compilation step to go wrong.

What the dashboard shows
  • Cumulative and period reach against target, by project and location
  • Full disaggregation views, since the disaggregation was fixed at Step 01
  • A data quality panel: records flagged as duplicates, records missing required disaggregation, submission gaps by site
Result
  • Tracking becomes a question you ask the dashboard rather than a task someone performs
  • Data quality problems surface as a visible count instead of being discovered at reporting time
Where this pattern earns its keep
  • Reporting deadlines stop being events. The figure exists continuously, so a donor request is a screenshot rather than a two-day compilation.
  • Duplicates become visible. Flagged rather than deleted, so someone with programme knowledge decides — not a formula.
  • New projects join without new infrastructure. One form, one warehouse, one dashboard; a new project is a new value in a field.
